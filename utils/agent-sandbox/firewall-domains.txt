# Azure DevOps Artifacts serves .nupkg *content* via a 302/303 redirect from the
# feed host to a regional Azure blob-storage account carrying a read-only SAS
# (e.g. m8vvsblobprodsu6weus76.blob.core.windows.net). Without this, the versions
# index resolves on the feed host but the nupkg download 403s at our own egress
# policy on the redirect target.
#
# The account name rotates by region but always carries the "vsblobprod" marker
# used by Azure DevOps package storage, so we scope to that rather than opening
# all of *.blob.core.windows.net (which is attacker-registrable — anyone can
# create an Azure storage account). NOTE: this is a blast-radius speed bump, not
# a wall — storage-account names are only globally unique, not substring-reserved,
# so a targeted attacker could register a "vsblobprod"-containing name. It blocks
# opportunistic exfil to arbitrary blob storage, consistent with the Phase D
# "control, not a wall" framing. (Glob entry — needs the '*' matcher below.)
*vsblobprod*.blob.core.windows.net
pypi.org
files.pythonhosted.org

# `gh run view --log-failed` / the Actions "download logs" API redirect from
# api.github.com to a per-run SAS URL on a sharded blob storage account, e.g.
# productionresultssa2.blob.core.windows.net. The shard number varies by run,
# so (as with vsblobprod above) we scope to the "productionresultssa" marker
# rather than opening all of *.blob.core.windows.net. Same caveat: this is a
# blast-radius speed bump, not a wall, since storage-account names are only
# globally unique, not substring-reserved.
#
# GitHub actually publishes the exact current shard list (productionresultssa0
# through productionresultssa19 as of writing) under domains.actions in
# https://api.github.com/meta, which would let this be an exact-match list
# instead of a glob - but that needs the policy loader to fetch and cache an
# external list rather than just reading a static file, which isn't wired up
# yet.
*productionresultssa*.blob.core.windows.net
results-receiver.actions.githubusercontent.com
